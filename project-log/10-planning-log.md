### ADR-001 [2026-05-21] Windows 桌面技术栈选择

**状态**：已采用

**替代关系**：无

**背景与需求**：ChromeIsolator 需要复刻 BrowserIsolator 的本地桌面体验，目标设备是 Windows 10 / Windows 11 x86-64。应用需要稳定管理窗口、系统托盘、文件系统、进程、回收站、剪贴板和安装包。

**采用的方案**：使用 C# / WPF / .NET 实现桌面应用，采用轻量 ViewModel / Service 分层。

**备选方案**：

1. WinUI 3
   - 优点：更现代的 Windows UI 技术。
   - 缺点：打包、部署和兼容性路径更复杂；对本项目需要的能力没有明显收益。
   - 放弃原因：当前目标是稳定复刻，WPF 更成熟直接。

2. Electron
   - 优点：前端开发生态丰富，跨平台能力强。
   - 缺点：体积大、资源占用高；本项目只做 Windows 版，不需要浏览器壳再套浏览器管理器。
   - 放弃原因：本地进程和系统集成是核心，Electron 成本偏高。

3. Tauri / Rust
   - 优点：体积小，系统能力强。
   - 缺点：Windows 桌面 UI、托盘、安装器、团队维护复杂度更高。
   - 放弃原因：对当前项目不是最低风险路径。

4. Qt
   - 优点：成熟跨平台 GUI。
   - 缺点：引入额外框架和授权 / 打包考虑；Windows 原生集成不如 WPF 直接。
   - 放弃原因：项目只面向 Windows。

**决策依据**：WPF 能满足 Windows 10/11 的原生桌面需求，进程管理、Shell API、托盘、剪贴板、文件夹打开和 MSI 打包路径成熟，适合本地优先工具。

**改动范围**：后续创建 `.sln`、WPF 应用项目、Service / ViewModel 目录和测试项目。

### ADR-002 [2026-05-21] 安装目录与用户数据目录

**状态**：已采用

**替代关系**：无

**背景与需求**：用户希望 Windows 版以可靠稳定的安装包分发。应用程序文件需要标准安装，profile 数据需要按用户隔离且普通用户可写。

**采用的方案**：使用安装包将主程序安装到 `%ProgramFiles%\ChromeIsolator`；配置和 Profiles 放到 `%LOCALAPPDATA%\ChromeIsolator`。如用户确认下载 Chrome 安装包，可临时缓存到 `%LOCALAPPDATA%\ChromeIsolator\Chrome`，但该目录不承载浏览器私有副本。

**备选方案**：

1. 全部安装到 Program Files
   - 优点：目录集中，像传统桌面软件。
   - 缺点：普通用户不可写，不适合 profile、配置、下载 Chrome 等运行时数据。
   - 放弃原因：会导致权限问题，也不适合多 Windows 用户隔离。

2. 全部放到用户目录绿色运行
   - 优点：无需管理员安装，升级简单。
   - 缺点：不像正式安装应用；开始菜单、卸载、升级路径不够规范。
   - 放弃原因：用户明确希望安装包可靠稳定。

**决策依据**：Windows 标准桌面应用通常将程序文件和用户数据分离。Program Files 提供稳定安装位置，LocalAppData 提供每用户可写数据目录。

**改动范围**：安装项目、路径常量、设置页、卸载策略和文档。

### ADR-003 [2026-05-21 / 2026-05-22 更新] Chrome 来源策略

**状态**：已采用

**替代关系**：被 ADR-008 收敛为最终实现策略；本条保留来源选择过程

**背景与需求**：Windows 版需要稳定获得 Chromium 浏览器运行时，并且用户明确要求不要使用 Chrome for Testing。项目使用场景包含 Douyin 等多账号登录，Testing 版本可能带来额外风控风险。用户也担心浏览器方案影响原本 Chrome 的插件、设置、登录用户和启动体验。

**采用的方案**：优先使用官方 Stable Chrome 程序文件。已安装 Chrome 时只复用 `chrome.exe`；未安装 Chrome 时，首次运行窗口说明隔离策略，用户明确确认后才下载并运行官方 Stable Chrome 安装包。Microsoft Edge Stable 作为备用 Chromium 引擎，仅在 Chrome 缺失且用户明确选择后启用。所有隔离环境必须强制使用 ChromeIsolator 自己的独立 `--user-data-dir`，绝不读取或修改用户默认 Chrome profile。

**备选方案**：

1. Chrome for Testing ZIP
   - 优点：ZIP 形态便于下载、解压和私有化；无安装器副作用。
   - 缺点：用户明确担心 Testing 版本在 Douyin 等场景触发风控。
   - 放弃原因：与用户需求冲突。

2. 官方 Chrome 安装器自动静默安装
   - 优点：官方 Stable，用户信任度高。
   - 缺点：可能注册 Google Update、写入系统或用户 Chrome 安装位置、创建快捷方式，可能影响用户已有 Chrome 安装状态。
   - 放弃原因：不能在用户不理解的情况下修改 Chrome 安装状态；安装必须用户确认。

3. 直接复用用户已有 `chrome.exe`
   - 优点：无需下载和安装 Chrome。
   - 缺点：依赖用户机器状态；Chrome 路径、版本、企业策略和更新状态不可控。
   - 采用结果：作为首选方案采用，但只复用程序文件，不读取默认 profile。

4. 第三方便携 Chromium
   - 优点：易于私有化。
   - 缺点：来源可信度、版本更新和媒体能力不可控；不是官方 Google Chrome。
   - 放弃原因：与官方 Chrome 目标不符。

5. Microsoft Edge Stable
   - 优点：Windows 10/11 通常自带，Chromium 内核，视频播放能力完整，稳定主流。
   - 缺点：不是 Chrome，产品名和用户预期仍以 Chrome 为主。
   - 采用结果：仅作为 Chrome 缺失时的用户确认备用引擎。

**决策依据**：用户要求不要 Testing，并且不能污染现有 Chrome。Chrome 程序文件和 profile 数据可以分离；共享程序文件不会导致登录态 / 插件串台，串台风险来自共享同一个 user data dir。安装 Chrome 属于系统 / 用户浏览器安装动作，必须显式确认。

**改动范围**：Chrome 下载器、安装 / 校验逻辑、设置页 Chrome 来源显示、错误提示、README。

**实现约束**：

- 不做 Chrome for Testing。
- 不做第三方便携 Chromium。
- 不做默认静默安装 Chrome。
- 不做 Windows 官方 Chrome MSI 私有提取 / 私有副本作为 MVP 路径。
- 不读写 `%LOCALAPPDATA%\Google\Chrome\User Data`。
- 启动环境必须使用 `%LOCALAPPDATA%\ChromeIsolator\Profiles\pN`。

### ADR-004 [2026-05-21] 指纹差异能力边界

**状态**：已采用

**替代关系**：无

**背景与需求**：BrowserIsolator 现有能力是通过 CDP 注入稳定的 `navigator.hardwareConcurrency` 和 `navigator.deviceMemory`。Windows 版要求从用户使用角度复刻，不扩大成复杂反检测平台。

**采用的方案**：仅复刻现有轻量差异：按环境编号稳定生成 CPU 核心数和内存值，并对已有页面和新页面持续注入。

**备选方案**：

1. 完整浏览器指纹模拟
   - 优点：表面上更接近反检测浏览器。
   - 缺点：范围大、风险高、维护成本高，也可能给用户错误预期。
   - 放弃原因：超出项目定位。

2. 不做任何指纹差异
   - 优点：实现简单。
   - 缺点：不符合 BrowserIsolator 已有功能。
   - 放弃原因：不是完整复刻。

**决策依据**：保留用户已经使用良好的现有功能，同时保持项目边界清晰，不承诺绕过风控。

**改动范围**：FingerprintInjector、环境详情高级信息、README 常见问题。

### ADR-005 [2026-05-21] Windows 安装包形式

**状态**：已采用

**替代关系**：无

**背景与需求**：用户希望 Windows 版提供可靠稳定的安装包，而不是只提供绿色 exe。

**采用的方案**：优先使用 WiX 构建 MSI 安装包。

**备选方案**：

1. 单文件 exe 绿色版
   - 优点：简单、无需安装。
   - 缺点：不符合用户对安装包稳定性的预期；开始菜单、卸载和升级体验较弱。
   - 放弃原因：用户明确偏好安装包。

2. MSIX
   - 优点：现代 Windows 打包格式，安装和卸载干净。
   - 缺点：签名、分发、权限和文件系统访问约束需要额外处理。
   - 放弃原因：当前项目优先传统稳定发布路径。

3. Inno Setup / NSIS
   - 优点：简单易用，适合传统安装器。
   - 缺点：MSI 在企业和标准 Windows 安装管理上更规范。
   - 放弃原因：优先 MSI；若 WiX 成本过高可重新评估。

**决策依据**：MSI 符合 Windows 传统软件安装、卸载和升级预期，适合安装到 Program Files。

**改动范围**：安装项目、发布脚本、部署文档。

### ADR-006 [2026-05-21] Windows 退出与托盘行为

**状态**：已采用

**替代关系**：无

**背景与需求**：BrowserIsolator 在 macOS 上关闭最后窗口后仍驻留菜单栏。Windows 需要提供等价体验。

**采用的方案**：主窗口点击关闭时隐藏到系统托盘；托盘菜单提供打开主窗口、启动 / 关闭环境、全部关闭、全部关闭并退出、检查更新、退出。真正退出时如果有运行环境，提示确认并关闭全部。

**备选方案**：

1. 点击窗口关闭即退出应用
   - 优点：行为简单。
   - 缺点：不复刻 macOS 菜单栏驻留体验，也会误关运行环境。
   - 放弃原因：不符合“完全复刻”。

2. 最小化到任务栏而非托盘
   - 优点：实现简单。
   - 缺点：快速启动 / 关闭入口弱，和原菜单栏体验不一致。
   - 放弃原因：系统托盘更接近 macOS 菜单栏。

**决策依据**：系统托盘是 Windows 上最接近 macOS 菜单栏驻留的交互模型。

**改动范围**：主窗口关闭逻辑、TrayService、退出确认、托盘菜单。

### ADR-007 [2026-05-21] 早期 Release 代码签名策略

**状态**：已采用

**替代关系**：无

**背景与需求**：Windows 未签名安装包可能触发 SmartScreen、浏览器下载警告或“未知发布者”提示。用户确认“有提示没关系，能用就行”，因此早期阶段应优先完成可用功能和安装包发布，不让代码签名证书采购阻塞开发。

**采用的方案**：早期 Release 允许未签名 MSI / EXE；README 明确提示可能出现 Windows 安全提示。发布脚本后续预留签名步骤但默认关闭。正式期如需要提升信任度，再购买 OV / EV Code Signing Certificate 并使用 `signtool` 签名主程序和安装包。

**备选方案**：

1. MVP 前必须购买代码签名证书
   - 优点：安装信任度更高，发布者信息更清晰。
   - 缺点：证书采购、组织验证、硬件 token / 云签名服务会拖慢早期功能开发。
   - 放弃原因：用户确认提示可接受，当前目标是先完成可用版本。

2. 永久不考虑签名
   - 优点：流程最简单。
   - 缺点：正式分发时用户信任感较差，下载和安装摩擦持续存在。
   - 放弃原因：签名仍作为后续质量目标保留。

**决策依据**：未签名只影响安装信任提示，不影响应用功能。ChromeIsolator 当前优先级是完成 Windows 版功能复刻和 GitHub Releases 发布闭环。

**改动范围**：部署文档、README 安装说明、后续 CI / 发布脚本。

### ADR-008 [2026-05-22] Chrome 使用与安装硬约束

**状态**：已采用

**替代关系**：补充 ADR-003

**背景与需求**：用户明确要求：大多数用户已经安装并日常使用 Chrome，ChromeIsolator 不能影响用户原本 Chrome 的插件、设置、登录用户、启动体验或用户选择提示。对没有安装 Chrome 的用户，应用可以帮助安装一个正常 Chrome；之后用户从桌面打开 Chrome 使用时，也不能和 ChromeIsolator 的隔离环境冲突。

**采用的方案**：ChromeIsolator 使用“Chrome 程序文件”和“Chrome profile 数据”彻底分离的策略。程序文件优先复用用户已安装的官方 Stable Chrome；如果未安装，则在用户明确确认后安装官方 Stable Chrome。无论 Chrome 来源如何，隔离环境启动时都必须传入 ChromeIsolator 自己的 `--user-data-dir`，绝不读取或修改用户默认 Chrome profile。

**备选方案**：

1. 自动静默安装 Chrome
   - 优点：首次使用路径短。
   - 缺点：可能在用户不理解的情况下修改系统 Chrome 安装状态。
   - 放弃原因：需要用户明确确认，避免误解和系统副作用。

2. 尝试提取私有 Chrome
   - 优点：理论上能拥有独立程序文件。
   - 缺点：官方 Windows MSI 不是面向私有提取分发；稳定性和授权边界不清晰。
   - 放弃原因：当前浏览器方案已定，不作为 MVP / 默认方案；只有 Google 提供明确可再分发、可私有部署的 Stable Chrome 包时才重新评估。

3. 使用用户默认 Chrome profile
   - 优点：实现简单。
   - 缺点：会影响用户插件、登录态、设置和默认 Chrome 使用体验。
   - 放弃原因：与用户硬约束冲突。

**决策依据**：Chrome 程序文件可以共享，但 profile 必须隔离。只要始终使用独立 `--user-data-dir`，用户正常打开桌面 Chrome 时仍使用默认 profile；ChromeIsolator 环境使用自己的 `Profiles\pN`，两者不冲突。

**改动范围**：ChromeManager、下载 / 安装确认 UI、README、设置页 Chrome 来源说明。

**实现原则**：

- 启动隔离环境必须传入 `--user-data-dir=%LOCALAPPDATA%\ChromeIsolator\Profiles\pN`。
- 不得读写 `%LOCALAPPDATA%\Google\Chrome\User Data`。
- 不得修改用户默认 Chrome profile、扩展、设置、登录用户。
- 如需安装 Chrome，必须先提示用户这是官方系统 Chrome 安装，可能触发 UAC。
- 安装 Chrome 后，用户从桌面启动 Chrome 应使用默认 profile；ChromeIsolator 环境仍使用独立 profile。
- Edge Stable 只作为 Chrome 缺失时的备用 Chromium 引擎，必须用户明确选择；Chrome 可用时始终优先 Chrome。

### ADR-009 [2026-05-22] 升级安装运行中检测与后续稳定性计划

**状态**：部分已实现，后续项待开发

**背景与需求**：用户担心下载安装新版本 MSI 后直接覆盖安装时，旧版 ChromeIsolator 仍在托盘运行，导致文件占用、旧进程继续运行、浏览器环境关闭不彻底或升级后状态异常。

**已采用的方案**：

- MSI 安装器增加运行中检测：若 `ChromeIsolator.exe` 正在运行，安装器提示用户先从系统托盘退出“浏览器多开”，再点击重试继续安装。
- 不使用安装器强制 kill `ChromeIsolator.exe`，因为强杀会绕过应用自己的 StopAll / OnExit 关闭逻辑，反而可能留下 Chrome 环境进程。
- WiX 构建脚本自动确保 `WixToolset.Util.wixext` 扩展可用，并在构建时引用该扩展。
- MSI 数据库 codepage 明确设为 UTF-8，避免中文快捷方式和运行中提示文案出现编码问题。

**后续开发计划**：

1. **升级安装验证矩阵**
   - 从 `1.2.0` 升级到更高版本，例如 `1.2.1`。
   - 分别验证应用未运行、主窗口运行、仅托盘驻留、多个环境运行中、Chrome 手动关闭后状态未刷新等场景。
   - 验证安装器提示“关闭后重试”的行为，确认 Retry 后继续安装，Abort 后不改动现有安装。

2. **启动时孤儿进程检测**
   - 启动 ChromeIsolator 时扫描是否存在由 ChromeIsolator profile 目录启动的残留 Chrome / Edge 进程。
   - 只识别命令行中包含 `%LOCALAPPDATA%\ChromeIsolator\Profiles\pN` 的进程，避免误杀用户普通 Chrome。
   - 先提示用户是否关闭残留环境，不默认强杀。

3. **卸载数据清理选项**
   - 当前策略是卸载程序但保留 `%LOCALAPPDATA%\ChromeIsolator` 用户数据。
   - 后续可增加“卸载时是否删除环境数据”的明确选择，或提供单独的“清理所有环境数据”工具入口。
   - 必须避免默认删除用户 profile，防止误删登录态、Cookie、扩展和密码。

4. **生命周期压力测试脚本**
   - 增加手动或自动压力测试清单：连续快速启动 / 关闭同一环境、多环境全部关闭、托盘退出、手动关闭 Chrome、安装升级前后残留检查。
   - 记录需要观察的指标：进程树是否残留、端口是否释放、UI 状态是否同步、句柄数是否持续增长。

5. **同版本安装包防误用**
   - 发布流程中明确禁止用同版本 MSI 当作升级包反复分发。
   - GitHub Release / 构建脚本继续要求 tag 和 `Directory.Build.props` 版本一致。
   - 后续可在安装器文档中增加“升级必须使用更高版本号”的说明。

6. **签名与发布质量**
   - 正式公开分发前补代码签名，降低 SmartScreen 和未知发布者提示。
   - 主程序和 MSI 都需要签名，并使用时间戳。

**改动范围**：安装项目、发布脚本、部署文档、后续测试脚本。
