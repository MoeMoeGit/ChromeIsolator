## 检查工具

在项目根目录运行：

```text
python handbook/tools/check_docs.py --strict-init
```

macOS 通常使用 `python3`，Windows 可使用 `py`。工具只读检查核心文件、Claude 导入、本地 Markdown 文件链接、00/01 初始化和篇幅；不验证业务事实、外网、锚点或模型是否遵守规则。

## 开发与协作

1. 检查 `git status --short --branch`、当前分支和 upstream；不覆盖、不清理、不自动纳入其他任务或用户的修改。
2. 结合 01、任务相关文档和代码明确“需求—现有实现—改动—验证”。小修简述即可，跨模块或长期行为变化再写计划。
3. 沿用当前分支。未经用户明确要求不新建或切换分支、不建工作树、不提交、不推送、不改版本、不打标签、不发布。
4. 需求范围内的实现直接完成；会改变产品含义、兼容性或长期边界的选择先讨论，并更新 11。
5. 结束前检查累计 diff 和关联路径，执行与风险相称的验证，只更新真正变化的状态和约定。

多人并行时在 01 按任务登记改动范围、负责人和依赖；登记不是文件锁，共享文件重叠时必须协调顺序。

## Git 与跨设备同步

- 文档整理和只读评审不自动合并远端代码。开发任务可 fetch；仅在工作区干净、upstream 明确且只落后时，才可按已授权流程快进。
- 工作区有修改时不自动 stash、reset 或清理。历史分叉先解释双方差异和整合方案，不自动 rebase、合并或强推。
- “推送 / 收工同步”包含提交本轮归属明确的改动并推送当前分支；推送前重新 fetch 并核实 upstream 和潜在 CI/Release 外部动作。
- 普通提交推送不等于版本发布。发布按 [08](08-deployment.md) 执行，标签必须匹配 `Directory.Build.props`。
- Git 无法看到另一设备尚未推送的工作。跨设备前应完成收工同步，用户 profile、依赖和构建目录不通过 Git 搬运。

## 日常收尾

- 按用户全部要求逐项核对，检查改动之间的交互影响；修复范围内确认的问题。
- UI 能运行时查看实际界面并检查入口、主操作、空/错/加载/禁用、多语言和窗口适配；静态检查或构建通过不能称为视觉验收。
- 跨平台结论分别报告。本项目在 macOS 的静态检查不代表 Windows WPF、托盘、注册表、Chrome 或 MSI 验证通过。
- 只清理本轮生成的临时产物；不删除用户文件、正式交付物或别人的未提交工作。
- 在 01 记录仍需跨对话交接的任务、风险、验证缺口和未同步状态；已稳定能力回到专题文档，不堆“已完成”列表。

## 专项评审与上下文维护

全面评审默认只读。报告区分确认问题、待验证风险和体验建议，并给出触发条件、位置、影响、证据和优先级；同一 AI 自查不称独立评审。

整理文档时保留当前约束、未解决问题、活跃交接和必要复现信息；已完成计划只提取长期结论，过期状态和纯过程删除。长样本、完整日志和原始报告按需独立存放并建立索引，不复制进日常必读文档。

## 信息保护

真实密钥、Cookie、密码、登录 profile 和敏感业务样本不得进入文档或 Git。示例使用占位值；发现凭据泄露时先说明范围，再按授权轮换。设备独有路径和临时状态不写成团队通用配置。
